There are two ways to connect an agent to Microsoft Teams. They differ in **who owns the Microsoft Teams bot**,
and that single difference decides how much Azure work you do.

| | StandIn Managed Bot | Bring your own Azure bot |
|---|---|---|
| Who owns the bot | StandIn | You |
| Azure app registration | none | you create it |
| App ID / client secret | none | you manage them |
| Install | add **StandIn** from the Microsoft Teams Store | upload your own app package |
| Identity in Microsoft Teams | appears as StandIn | appears as your own bot |
| Best for | getting working quickly | full identity custody |

Both modes connect **your own agent**: StandIn is the bridge, never the brain. And both need the same
one-time admin consent before calling works - chat works without it.

## StandIn Managed Bot

StandIn publishes and operates one Microsoft Teams bot; your Microsoft organization is routed to your agent by
a connection you create in the StandIn portal.

1. In Microsoft Teams, add **StandIn** from the Store.
2. Type `signin` to the bot and sign in with your StandIn account. That link is how StandIn learns
   which Microsoft organization to connect - you do not type a tenant id anywhere.
3. In the StandIn portal, deploy an identity and choose **Use the StandIn bot**. Paste your agent's
   address; the portal gives you back the secrets.
4. A Microsoft 365 administrator approves calling once for the organization. Chat works before this;
   calling switches on when the approval lands.

You get a **connection secret**, and on the consolidated SDK it is one environment variable:

```bash
export STANDIN_SECRET='<the connection secret from the portal>'
```

A managed deployment may issue a **second key for chat**. That is deliberate, not an oversight:
each lane signs its own handshake, so two keys mean a key that can open one lane cannot open the
other. If you are given one, export it as `STANDIN_CHAT_SECRET` and the chat lane signs with that
instead. `ChatChannel` reads `STANDIN_CHAT_SECRET` first and falls back to `STANDIN_SECRET`, so
when a single key covers both lanes there is nothing extra to set.

The managed bot is also what unlocks the SDK's chat lane. `ChatChannel` dials **out** to StandIn
with whichever of those two keys it found, so chat needs no URL registered, no open port and no
tunnel rule, and your agent never holds a Bot Framework credential. It needs no flag either: if the
socket opens, you are managed.

<Note>
Running one of the older standalone bridges instead? Their managed chat lane is an inbound listener
with its own port and path, configured in the runtime's plugin block rather than in the environment.
That belongs to the bridge rather than to this SDK, which is why it is not documented here: this
SDK's chat lane is dialled outbound and needs neither a port nor a mount.
</Note>

<Note>
One agent instance serves **one** connection. The secrets belong to a single Microsoft organization -
run a second instance for a second organization, and never share a secret across tenants.
</Note>

## Bring your own Azure bot

You register a Microsoft Entra app, create an Azure Bot resource, and upload your own Microsoft Teams app
package. The bot carries your name and lives entirely in your tenant. Follow
[Azure bot setup](/teams/azure-bot) and [App package](/teams/app-package).

This is the right choice when identity custody matters more than setup time, or when you need the bot
to be visibly yours.

## Endpoints

StandIn dials your agent, so the endpoint you save in the portal has to match the path your agent
actually listens on. Give the portal a bare host and it fills in the default below; paste a full URL
instead if your bridge serves something else.

**Calling is the same in both modes.** Only chat differs, and that is the line people get wrong:

| Lane | Public path | Local target |
|---|---|---|
| Calling (media WebSocket), both modes | `wss://host/msteams/calling` | `127.0.0.1:9442`, path `/msteams/calling` |
| Chat, **StandIn Managed Bot**, consolidated SDK | none: the worker dials out | nothing to expose |
| Chat, **bring your own Azure bot** | `https://host/api/messages` | `127.0.0.1:3978`, path `/api/messages` |
| Chat, **StandIn Managed Bot**, legacy standalone bridge | `https://host/msteams/messages` | `127.0.0.1:9444`, path `/msteams/messages` |

A **bring-your-own-bot** identity uses `/api/messages`, served by your runtime's own Microsoft Teams channel
(OpenClaw's `msteams` channel, the Hermes gateway's Microsoft Teams platform) rather than by anything in this
SDK. That is a different process from calls, which is why it has its own port. The portal suggests
the right value when you deploy the identity, so take the one it offers.
